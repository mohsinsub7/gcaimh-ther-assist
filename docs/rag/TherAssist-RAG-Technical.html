TherAssist · Retrieval-augmented guidance

How the corpus shapes every suggestion

Technical reference for the engineering team. Every card, metric and summary TherAssist shows is generated after the model has read passages retrieved from a clinician-curated corpus held in Vertex AI Search. There is no path that skips retrieval. This page explains where retrieval happens, what triggers it, exactly what is sent and returned, and how to prove from the logs that it ran.

01Where retrieval happens

Retrieval runs in three places, using two mechanisms: the backend searches the datastores itself for the real-time path, and Gemini searches them through grounding tools for the deeper paths.

Words become a transcript; the transcript drives three retrieval-backed calls; only the model outputs on the right reach the therapist.

Routing map

modality_map in main.py line 580 (and MODALITY_RAG_MAP for the tool path): CBT → cbt-corpus + ba-corpus; DBT → dbt-corpus; IPT → ipt-corpus; unknown → CBT. ebt-corpus and safety-crisis are always added.

How documents are chunked

Vertex AI Search's layout parser reads each PDF, then layout-based chunking cuts it into 300–500-token chunks with the section's ancestor headings prepended, so every chunk carries its context.

Standard edition = snippets

The datastores are standard edition (SOLUTION_TYPE_SEARCH). Search returns snippets (a highlighted 1–3 sentence extract around the matching terms) plus document metadata.

03What triggers a lookup, and what is searched

A lookup is started by the transcript, not by a keyword. The last ~200 words of what was said become the search query; the patient's own words do the looking up.

  • Trigger.NewTherSession.tsx · WORDS_PER_ANALYSIS = 8
    When ≥8 new final-transcript words have accumulated, the frontend sends the last 5 minutes of transcript (final lines only, speaker-labelled), the session context and a shared job id. If no trigger has fired 20 s after the first words, a time-based fallback fires once.
  • Query.main.py · prefetch_rag_context, line 586
    The transcript text is joined and its last 200 words become the query. No keyword extraction, no rewriting.
  • Shelves.4 datastores in parallel · 10 s cap each · 25 s cache
    ebt-corpus and safety-crisis always, plus the modality's corpora. Results are cached per modality, keyed on a hash of the last 500 characters.
  • Safety scanner.constants.py · SAFETY_KEYWORDS, 94 terms in 5 lists
    Deterministic substring match before any model call: suicidal ideation (19), self-harm (14), violence/homicide (22), abuse disclosure (22), substance crisis (17). A hit forces category=safety, timing=now, injects the matched terms into the prompt and raises the comprehensive thinking budget to 16,384.
  • Trigger phrases.constants.py · TRIGGER_PHRASES
    Four demo phrases ("something else came up", "scared but I want to do it", "very brave", "I might fall apart") switch the real-time prompt to its non-strict variant. They do not change what is retrieved.

What never triggers retrieval: interim (partial) transcript lines, clinician notes, and anything typed in the UI.

04The real-time path, step by step

1.3–2.5 s end to end, of which 0.3–1.2 s is retrieval. The model never sees the transcript without the retrieved passages in front of it.

Alert JSON schema (model output)

{
  "alert": {
    "timing": "now | pause | info",
    "category": "safety | technique | pathway_change | engagement | process",
    "title": "Brief descriptive title",
    "message": "Specific action or observation (1-3 sentences)",
    "evidence": ["quote(s) from the patient"],
    "recommendation": ["up to 3 actions"],
    "immediateActions": ["step to take right now"],
    "contraindications": ["what to avoid"],
    "crisis_resources": ["required for safety alerts, e.g. 988 Suicide & Crisis Lifeline"]
  }
}

The backend adds timestamp, session_phase, analysis_type, prompt_used (strict / non-strict), trigger_phrase_detected, safety_keywords_detected, job_id and _diagnostics (model, latency_ms, ttft_ms, token_usage incl. thinking tokens, finish_reason, rag_tools, grounding.chunks_retrieved, json_parse_success, used_fallback). The frontend then de-duplicates (Jaccard similarity on title and message, 3 s hard block, per-category throttles) and shows the card.

05Comprehensive and summary paths

Here Gemini searches the corpus itself: the datastores are attached as Vertex AI Search grounding tools, the model issues its own queries while reasoning, and every passage it relies on comes back as a grounding chunk that becomes a citation.

Tools are built once at import time (MANUAL_RAG_TOOL, SAFETY_RAG_TOOL, CBT_RAG_TOOL, BA_RAG_TOOL, DBT_RAG_TOOL, IPT_RAG_TOOL, TRANSCRIPT_RAG_TOOL). Grounding chunks arrive in candidates[0].grounding_metadata.grounding_chunks[] with retrieved_context.title and .text; the summary copies them into citations[] = {citation_number, source}, which is why a summary response is ~143 KB of which ~133 KB is citation text.

Cache behaviour

Results are cached 25 s per modality; within a burst of triggers a cache hit shows no new query line. Normal.

Permissions and network

Runtime SA 420536872556-compute@… holds discoveryengine.viewer and aiplatform.user, with egress to us-discoveryengine.googleapis.com through one shared gRPC client.

What is deliberately not retrieved: clinician notes, the patient record, prior sessions' transcripts, anything typed in the UI. Configuration lives in constants.py (models, prompts, safety keyword lists, trigger phrases) and main.py (modality_map, RAG_CACHE_TTL_SECONDS = 25, page_size = 3, 10 s search timeout). The rule for the project: local and online always run through these datastores, and every deploy is checked against the log lines above.

08Deployment facts that affect retrieval

Online topology

One Cloud Run service, ther-assist-sidecar: nginx (:8080) → analysis :8081, storage :8082, websocket :8083. Ingress all, IAP on, invoker = IAP service agent only. Same code, same datastores as the local stack.

Identity behind IAP

Users sign in through IAP with their SUNY workforce identity; IAP forwards a signed X-Goog-IAP-JWT-Assertion with each request, and only the IAP service agent can invoke the service.
